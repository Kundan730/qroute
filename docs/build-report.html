What the brief asked for, and where it is

Five deliverables were specified. Each is built, and each has evidence behind it rather than an assertion.

01

Graph-based network model

Three Indian city extracts from OpenStreetMap, with free-flow speeds imputed by road class because Indian OSM data carries almost no speed tags. Edge weights update in place as traffic changes, with no graph rebuild.

Koramangala: 13,343 nodes, 34,266 directed edges, 2,050 km of road. All 34k weights recomputed in 7.8 ms.
02

Mathematical formulation

A two-index model with single-commodity flow for capacity and subtour elimination, big-M time propagation for windows, and a weighted time, distance and congestion objective. Every constraint is mapped to the code that enforces it.

Congestion is defined twice on purpose: a bounded delay fraction for the objective, an unbounded delay ratio for the map. Relation verified.
03

Quantum-inspired algorithm module

Two engines. A quantum-behaved particle swarm sampling from a delta potential well, and a second engine applying genuine Han–Kim rotation gates to a qubit register. Both are classical simulations, and the documentation says so.

Rotation gate verified orthogonal; amplitudes stay normalised under repeated rotation.
04

Software platform

A service with 21 endpoints streaming live optimisation progress, a nine-command terminal interface, and a map application where you set the hour of day, block a lane, and watch the routes change.

Driven end to end in a browser: instance generated on real intersections, solved to a feasible five-vehicle plan.
05

Demonstration and benchmarking

Ten seeds per solver at an equal wall-clock budget, one thread each, gaps measured against published best-known costs and, where an exact solver can close the instance, against proven optima.

Friedman test over 16 instances, p = 1.25×10⁻⁹, with Holm-corrected pairwise comparisons.

What we claim, and what we do not

The problem statement asks for a quantum-inspired method benchmarked against conventional metaheuristics. That comparison came out positive. Several others did not, and both belong in the same table.

Confirmed

The quantum-behaved swarm beats the classical swarm it derives from

Under an identical decoder, local search and budget, across 170 paired runs. This is the comparison the brief actually asks for.

0.87% against 1.03% · p = 1.3×10⁻⁶ · effect size 0.62

Confirmed

It also beats simulated annealing, multi-start local search and OR-Tools

All significant after Holm correction for multiple comparisons. The rotation-gate engine does better still: it is statistically indistinguishable from the genetic algorithm, the strongest classical method here.

vs annealing p = 0.0028 · vs multi-start p = 6.5×10⁻⁹ · vs OR-Tools p = 5.2×10⁻¹⁶ · rotation gate vs GA p = 0.087, not separable

Confirmed

The standard contraction coefficient is wrong for this encoding

Under a random-key representation only the induced ordering matters, so the smallest meaningful change is one rank. The published range makes the sampling step about twenty times too large. Reducing it cut the median gap from 0.77% to 0.25%.

p = 1.3×10⁻⁴, reproduced across two independent runs of 80 and 88 pairs

Bounded

It does not beat every classical method

The genetic algorithm and ant colony optimisation are both significantly better than the swarm. PyVRP, a specialised state-of-the-art solver, is ahead of everything at 0.23%. Every table says so.

Refuted

The step size does not scale with instance size

We predicted the right coefficient should follow 1/n and that this would fix the largest instance. Tested across eleven instances up to two hundred customers, it is indistinguishable from a fixed constant and no better where it mattered. The prediction was wrong and is recorded as such.

p = 0.42 over 88 paired runs

Refuted

No quantum advantage, and no quantum hardware

Both engines are classical algorithms whose update rules borrow their form from quantum mechanics. Asymptotic complexity is unchanged. Single-pair shortest paths are solved exactly by Dijkstra and A*, never by a metaheuristic.

Defects found by running it

Each of these produced a plausible-looking but wrong result, and none was caught by reading the code. They are listed because the same mistakes are easy to make again.

Segment reversal was priced wrongly on one-way streets

The 2-opt operator used the four-arc shortcut that is only valid on symmetric cost matrices. Real road networks are asymmetric, so it silently accepted moves that made routes longer.

Would have corrupted every road-network result.

The swarm's contraction never happened

The coefficient was indexed on the iteration cap, which time-budgeted runs leave effectively infinite. The progress fraction stayed near zero and the exploration-to-exploitation transition, the algorithm's central mechanism, never ran.

Found by noticing a longer run scored worse than a shorter one.

Two solvers minimised different objectives

The quantum swarm hard-coded a constraint penalty of 1000 while every other solver inherited an instance-scaled value near 16. The comparison between them was not a comparison, and it invalidated a whole ablation.

Found by an adversarial review pass, not by the tests.

Infeasible runs were averaged into headline gaps

An overloaded plan can be arbitrarily cheap, so including it flattered an algorithm exactly when it had failed. Three solvers appeared to beat a published optimum, which is impossible. One scored 5.6% where the honest figure was 10.6%.

A regression test now asserts no result set can report a negative gap.

A repair pass undid its own work

After splitting off an overloaded route, it polished the result under ordinary penalties, which merged the routes again. Forty forced overloads left three unrepaired; all forty now repair.

Its failures were also being swallowed by a bare exception handler.

Three solvers never received the budget they were credited with

The benchmark dispatcher inspected a thin wrapper's parameter names, found neither the time budget nor the seed among them, and forwarded neither. PyVRP and OR-Tools ran at their own ten-second defaults against everyone else's twenty, and PyVRP got seed zero for all ten of its supposedly independent runs. The fairness claim on which the whole comparison rests was false.

Dropping a keyword argument raises nothing, so a verification pass had already missed it. Every figure on this page is from the corrected re-run.

Concurrent requests bypassed the run limit

The service checked its capacity before registering the run, so six simultaneous requests all succeeded against a cap of four.

Sequential requests behaved correctly, which is why it went unnoticed.

The demonstration

Forty deliveries across Koramangala, Bengaluru, under morning traffic, then disrupted.

These figures are being re-measured

An audit found that the disruption table previously shown here came from an ad-hoc script rather than from the documented command, and did not reproduce from it. Two statements were also wrong on their face: the disruption was described as a blocked lane when the code injects a speed reduction, and the slowdown was given as a factor of 49, which a speed multiplier of one tenth cannot produce because it caps the increase at ten-fold.

The numbers return when they have been regenerated from the documented command with every flag pinned. Nothing unverified is quoted in the meantime.

The mechanism is real and implemented: the platform rebuilds its travel-time matrices under the new weights, prices the existing plan against them, and re-optimises both cold and from a warm start seeded with the previous solution. The command reports which start won on that run, including when the warm start loses.

Where the honesty machinery shows

The search first returned a plan two units over capacity on one vehicle, because it is deliberately allowed to cross infeasible ground where the good moves are. A repair pass escalates the penalties until the plan is dispatchable, which cost 5% more vehicle time.

The platform reports the feasible, more expensive plan. Not the cheaper impossible one.

Before you submit

Two things about the submission itself, verified against the official guidelines rather than the listing.

The statement can close before the deadline does

Submission closes 20 September 2026, but each problem statement freezes once 500 ideas are submitted. The public counter sits next to PS 26137 on the portal. Check it early.

What the evaluation actually names

Novelty, complexity, clarity and detail in the prescribed format, feasibility, practicability, sustainability, scale of impact, user experience, and potential for future work. Only four to five teams per statement reach the finale, and the sponsoring organisation is not obliged to pick a winner.

All figures measured on an Apple M4 with ten cores, single-threaded per run, on 3 September 2026. Benchmark instances are CVRPLIB and Solomon; road network data is © OpenStreetMap contributors, ODbL.
